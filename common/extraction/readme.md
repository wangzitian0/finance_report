# `extraction` — statement parsing bounded context

> Owned spec for document upload, OCR/LLM parsing, reviewed envelopes, and statement-run orchestration. Conforming implementation: [`apps/backend/src/extraction/`](../../apps/backend/src/extraction/). Audit case registry: [`audit-failed-cases.yaml`](./audit-failed-cases.yaml). See also: `common/ledger/readme.md#decimal-rule`, `common/ledger/readme.md#async-tx-boundary`, `common/reconciliation/readme.md#thresholds`.

## Overview

- PDF/image extraction uses the multimodal role (`LLM_MULTIMODAL_MODEL`, defaulted by `infra2_sdk.runtime.llm.LlmSettings`); CSV/text structuring uses `LLM_SMALL_MODEL`. No model names are hardcoded here, and there is no fallback model chain.
- Z.AI vision renders PDFs in lazy 5-page batches (`PDF_VISION_MAX_PAGES`), running split header+rows extraction (`build_meta_prompt` + `build_rows_prompt`) on single-batch vision uploads, two-stage metadata+body extraction when page count exceeds 5, and reading native page text first when the text layer prints decimal amounts.
- **Check feedback loop (#2964):** each pass of a bank statement gives one reading for each account. `document_findings` (`base/findings.py`) returns one typed `Finding` for each failed check: `no_rows`, `missing_fact`, `row_invalid`, `balance_mismatch`, `opening_not_in_text`, `closing_not_in_text`, `rows_not_in_text`. A document without rows is correct when a balance equation holds. A kept pass with no finding ends the loop. Otherwise the next pass gets the findings of the kept pass as one prompt block (`check_feedback_block`; each value of the reading is a printable-ASCII JSON string of at most 40 characters, a line names its account when the document has several, and the block holds at most 30 findings with a balance gap first) and reads the text layer again. A balance gap sends the last pass to the page images. `replaces` decides whether a later pass replaces the kept pass. A pass without rows never replaces a pass with rows. A reading that the persist step cannot store (no row, or an invalid row) loses to each reading that it can store. A kept pass with a balance gap is replaced by a pass with a smaller gap. Apart from that, a later pass never loses evidence: it has no fewer accounts with rows; it states the opening balance and the closing balance for no fewer accounts (each one unless the text check showed that the document does not print it); and it has no fewer rows, unless each of its rows is proven and it has more proven rows than the kept pass. A row is proven when its account holds the balance equation on a balance pair that the text prints (for a source without a text layer, on the stated pair). Then the lower rank wins: usable, no balance gap, smaller gap, more proven rows, fewer findings. A later pass that raises keeps the kept pass. A brokerage reading replaces only a kept pass that is unusable or has a balance gap. A pass that does not improve the kept pass ends the loop, unless a balance gap remains. `AI_EXTRACT_MAX_ATTEMPTS` (default 3) limits the passes. Human review gets the kept pass when findings stay.

## Statement ingestion application boundary

- `StatementIngestionUseCase` owns load -> extract -> persist -> promote/review -> posting across API and Prefect workers.
- Upload atomically stores object bytes, creates `UploadedDocument` (ODS) keyed by `(user_id, file_hash)` via savepoint race recovery, binds `StatementSummary` (DWD), and enqueues an extract `StatementRun`.
- `DELETE /statements/{id}` retires (`RETIRED`) the statement and releases only transactions no longer owned by an active/approved statement (`release_transaction_dispositions` -> `VOID` entries under user advisory lock) while preserving stored artifacts and audit lineage.

## Extraction Result And Economic Disposition

- `parse_document` emits an immutable `StatementExtractionResult` (`source_type` bank|brokerage, `evidence_type` `transaction_ledger`|`position_snapshot`); re-parsing advances `StatementSummary.current_extraction_result_id` without overwriting history.
- `DispositionPolicy` consumes typed `IntentProposal`, reviewed counter-account, and active reconciliation transfers (`accepted` matches outrank proposals) to produce balanced ledger commands under `StatementDispositionPolicySnapshot`.
- `auto_accept_ai_suggestions` (default enabled under `AUTO_ACCEPT_AI_SUGGESTIONS`) applies score `>= 60` proposals or routes fallback rows to General Income/Expense (`UNCLASSIFIED`), holding ambiguous transfers/investments in suspense; with auto-accept off, rows in `60-84` remain drafts until one-click/manual approval.
- Background classification runs asynchronously as a `classify` `StatementRun` (180s phase deadline; at most 50 rows/batch, 4 parallel batches) with separate sessions per phase so no DB transaction or policy lock is held across LLM calls (`#3028`). A model call happens only inside a `classify` run: the approve and the one-click fill ask no model, and a row without an answer posts to the General account (`#2994`).

## Upload-First Product Contract

- Bank and brokerage statements are `supported`; CSV exports, ESOP/RSU, property, liability, and manual records are `manual_trusted`; settlement notes are `gap`.

## Data Models

- **Vocabulary** (`src/extraction/base/source_vocabulary.py`): `DocumentType`, `DocumentStatus`, `TransactionDirection`, `RuleType`, `ClassificationStatus`, `BankStatementStatus`, `Stage1Status`.
- **ODS (`UploadedDocument`) & DWD (`AtomicTransaction`, `AtomicPosition`, `StatementSummary`)**: immutable atomic facts keyed by custody scope (`AtomicTransactionIdentity`) and per-currency balance containers (`currency_balances` reconciled independently via [per-currency balance reconciliation](../reconciliation/readme.md#per-currency-balance-reconciliation)).
- **Reviewed envelope (`ReviewedStatementEnvelope`)**: append-only `POST /api/statements/{id}/review-envelopes` decision filling absent institution/custody/currency/period/balance facts without mutating source extractions. A transaction-ledger source without an institution keeps its rows with `institution` NULL and the missing fact `institution`; the confirmation must state the institution and never replaces an institution that the source states (#3167). A position snapshot without an institution is rejected.
- **Consolidated multi-account PDFs (`#2983`, `#2987`)**: `split_paged_extractions_by_account` and `split_multi_account_extraction` partition multi-account payloads into `1..N` sibling `StatementSummary` rows (`(user_id, file_hash, sub_account_key)`) under one `UploadedDocument` with independent custody binding, balance validation, trace records, and classify runs. `pdf_text_layer.py` preserves visual column offsets when dual Debit/Credit headers exist.
- **Package interface**: `resolve_statement_contribution()` and `list_statement_contributions()` publish `ResolvedStatementContribution` with `TraceDecisionRef` (`authoritative` vs `unproven`) for reporting.

## <a id="confidence-scoring"></a>Confidence Scoring

- Multi-channel evidence combination (`compute_confidence_breakdown` in `extraction/base/validation.py`): active independent channels combine as `1 - prod(1 - p_k)`.

| Channel | Reliability (`p_k`) | Condition |
|---|---|---|
| Printed balance equation (`A1 + sum(B) == A2`) | `0.75` | Printed opening and closing balances present and balanced (`#3112`: never self-derived from row 1) |
| Source text / CSV proof | `0.85` | PDF text layer verifies printed balances and >= 80% row amounts (`check_closing_balance_against_text`), or declared CSV |
| Split header vs rows check | `0.45` | Independent header/balance call agrees with row-extraction call |
| Running balance progression | `0.35 * ratio` | Consecutive `balance_after` steps reconcile within tolerance |

- `>= 85`: eligible for auto-accept only after printed balance validation, independent source proof (`source_verified=True`), custody mapping, and non-overlapping source period checks pass.
- Image uploads and scanned PDFs (`TEXT_UNUSABLE`) are correlation-capped (`<= 80`) and routed to `parsed` (`pending_review`, `#2918`).
- Missing printed opening/closing balances (`balance_proof_available=False`) or printed opening/closing balances absent from a readable PDF text layer (`OPENING_NOT_IN_TEXT` / `CLOSING_NOT_IN_TEXT`) force `balance_validated` non-`True` (`None` when unprinted, `False` when absent from text) and cap confidence at `<= 59`, requiring explicit Stage-1 confirmation or reviewed envelope without fabricating opening/closing balances (`#3112`).
- Brokerage under-extraction (`< 2` txns) is capped at `UNDER_EXTRACTION_SCORE_CAP` (`60`).

## Brokerage Position Import

- Broker documents (IBKR, Moomoo, Futu, Fidelity, Charles Schwab, Pershing, Vanguard, E\*TRADE, TD Ameritrade, Saxo, Tiger Brokers) route to `BROKERAGE_POSITIONS_PROMPT` before the model call and import into `AtomicPosition` + `ManagedPosition` via `POST /api/portfolio/brokerage-imports` (`BrokeragePositionImportService`).
- Text-layer brokerage parses with `positions` return directly without vision fallback, and consolidated brokerage merges permit multiple subaccount suffixes (`allow_multiple_accounts=True`).
- Import failures persist non-destructively in `extraction_metadata["brokerage_import_failure"]` (`record_brokerage_import_failure` / `clear_brokerage_import_failure`). Missing snapshot dates, zero extracted positions (`brokerage_positions_missing`), or out-of-range/non-ISO-4217 values return HTTP 422 (`brokerage_snapshot_date_missing`, `brokerage_positions_missing`, `brokerage_position_out_of_range`).

## Credit Card Liability Custody

- Credit card statements (`is_credit_card_statement` via card markers or `opening_balance < 0` with `closing_balance <= 0`) bind `AUTO-CARD` `AccountType.LIABILITY` accounts instead of `AUTO-BANK` `ASSET` accounts.
- `statement_balance_to_ledger_amount` negates statement debt balances into positive credit-normal `LIABILITY` ledger positions, and `coverage_bank_custody_account_ids` excludes `LIABILITY` custody from Cash Flow cash.

## Statement run

- `statement_runs` tracks every `extract` and `classify` attempt (`requested -> running -> succeeded | failed | cancelled`) with partial unique index `uq_statement_runs_one_active` guaranteeing at most one active run per statement (`409` with `active_run_id`).
- State transitions go exclusively through conditional updates in `extension/statement_runs.py`, emitting `TraceRecord` events under `statement:{statement_id}:run:{run_id}`.
- `start_user_extract_run` locks the statement `FOR NO KEY UPDATE` (`key_share=True`) before inserting a run; `reap_stale_runs` fails stale `requested` (`claim_timeout`) or `running` (`heartbeat_lost`) runs after 5 minutes. Frontend `PARSING_TIMEOUT_MS` (7 minutes) exceeds this reaper window, and `scripts/prefect_worker_entrypoint.sh` bounds concurrent process flow runs via `--limit`.
- Completed extraction runs record non-null `resolved_model_id` and a model-agnostic `artifact_dependency_digest` (`extraction_artifact_dependency_digest` over source hash, preprocess version, pinned prompt fingerprint, schema version, normalizer version, and hints) under `extraction_metadata["artifact_provenance"]`; consolidated multi-account siblings also record their own `EXTRACT` run with `auto_approve_candidate` and `artifact_provenance`.
- High-confidence statements (`auto_approve_candidate=True`) approve and finish their `classify` run atomically in one transaction (`approve_statement_workflow(..., ignore_run_id=run_id)`).
- `RunHints` accepts `<= 20` keywords (`<= 64` chars) and a `<= 500`-char note, hashed by `run_prompt_digest` into `prompt_digest` with `model` and the template version of the run kind (`PARSING_PROMPT_TEMPLATE_VERSION` or `CLASSIFICATION_PROMPT_TEMPLATE_VERSION`). Every run stores both columns at creation.
- **Classify again with hints (#2994, S4b-1).** `POST /statements/{id}/runs` takes `kind` `extract` or `classify` and `hints`. The body has no `model` field: a body with `model` gives 422, and the route never reads the model catalog (#2953). The run uses the model role of the environment. A classify run needs a `PARSED` statement (else 400; 409 if the status changed under the lock). Hints are allowed for every file type, because the model classifies the rows of a CSV too: `hints_apply_to_file_type` is an extraction rule only. `start_user_classify_run` shares `_start_user_run` with `start_user_extract_run`: the statement lock first, then the run insert with the latest run as parent, no status change, no commit. The route commits, then `submit_classify_run` runs `execute_classify_run` as a tracked task of the API process. If the task cannot start, the run fails with `dispatch_failed` (503). If the process dies, the run stays `requested` and the reaper fails it with `claim_timeout` after 5 minutes: the user starts it again.
- **Prompts and hints.** The executor reads the hints of its own run row, after the claim committed, and loads user correction few-shot examples in Phase a (`get_few_shot_examples`) before releasing the DB session. `ask_model` passes hints/few-shot examples to the proposer only when they are not empty. `prompts/hints.py` holds the header, the JSON encoding (keywords as an array, the note as a string) and the end line, shared by both prompts. Each prompt adds its own purpose line. Extraction keeps the line of S2, so its prompt with hints is byte-identical and `PARSING_PROMPT_TEMPLATE_VERSION` is `2`. Classification says that the hints may decide the category of the rows or descriptions that they name, and never change the catalog, the output schema, the signs or the amounts (`CLASSIFICATION_PROMPT_TEMPLATE_VERSION` is `3`). With empty hints and no correction examples the classification prompt is byte-identical to the prompt before S4b-1. One fingerprint of each prompt is pinned to its version. An answer outside the catalog still counts under `other` and writes no row.
- **Re-ask.** An automatic classify run, and a user run with no hints, ask only rows without an answer. A user classify run (trigger `rerun`) with hints asks again for each row with a model answer. It skips a keyword-rule row, a row that the user decided (`corrected_by_user`, `rejected_by_user`, `accepted_by_user`), a row that the ledger covers (`ledger_covered_txn_ids`: an anchored entry, a legacy entry, an accepted transfer match) and a row whose live answer came from a run of the same statement with the same `prompt_digest`, so a run that failed resumes. A re-ask appends: the batch write inserts the new answer and sets the old one to `SUPERSEDED` with `superseded_by_id`. The key `uq_txn_classification_version` is a partial unique index on `draft` and `applied` rows (migration 0076), so history rows are allowed. A query with no status or with a bound status cannot use a partial index, so `ix_txn_classification_txn_rule` keeps the lookups by row indexed. The batch write takes the policy-rule key, locks the answer rows `FOR UPDATE ORDER BY id`, and reads the decisions and the ledger coverage again. `apply_suggestion_feedback` takes the key before the row, as a correction does. The insert of an answer takes FOR KEY SHARE on the transaction row and on the account, so a poster locks both with FOR NO KEY UPDATE (`submit_reviewed_disposition`, the claim of the reconciliation repository). `settle_drafts_after_posting` locks the drafts and reads them again. The auto-fill of the approve takes the statement lock before it looks for an active run, so a run start waits for the approve or the approve refuses with the run id. A row for which the model returns no answer keeps its old answer; a low-confidence answer is written as the fallback row (AC 141). Rows of other policy versions are left to the sweep.
- **Extraction call and the retry loop (#3153).** `_extract_json_with_model` calls the model entry point and maps `ModelCallFailed.kind` to the `ExtractionError` kinds: `rate_limit` and `usage_limit` give `rate_limit`; `timeout` gives `timeout`; `unavailable`, `rejected` and `not_configured` give `http_error`; `bad_reply` and `unclassified` give `model_error`. A reply that `json.loads` cannot read (also nesting that raises `RecursionError`) is `json_parse`. The retry loop keeps an earlier pass when a later pass raises `ExtractionError`, `ValueError`, `ArithmeticError`, `LookupError`, `AttributeError` or `TypeError`: the errors of a failed model call and of a reading of the wrong shape. A page that MuPDF cannot draw is an `ExtractionError` (`Failed to render page N`), so it belongs to that group. An error of another class is a bug and ends the loop with its own error. The log line "keeping the best pass" has `ended_on_failure` (true when the last pass failed) and `failed_pass`.
- **Model failures in a classify run (#3153).** `_propose_batch` raises `ModelCallFailed` for a failed call and for a reply that is no JSON array (`bad_reply`). A model that leaves rows out of a valid list is not a failure: those rows stay without an answer. `execute_classify_run` catches `ModelCallFailed` for each batch and nothing broader: the rows of that batch get no answer, and `result_summary.model_failures` counts the failed batches by kind. A run in which every batch failed ends `failed` with `classification_failed` (the run row has no `result_summary`: its message names the kinds, and the audit event `statement.classification.failed` carries the counts), and it skips the auto-approve: the statement keeps its rows and the approve sends them to the economic review. The exception is a deployment with no model configured (every failure is `not_configured`): the run ends `skipped_disabled` as when the model is off, keyword rules answer, the auto-approve is tried, and the rows without an answer wait for the economic review as before. Each batch makes at most 2 attempts of 60 s, inside the deadline of the run. Another error is a bug: it fails the run with its class in the log. The AI column mapping of a CSV raises `ExtractionError("AI column mapping unavailable (<kind>)")` from the `ModelCallFailed`; a mapping that matches no row keeps "No valid transactions found", and so does a deployment with no AI configured (`not_configured`: there is no AI fallback).
- **Run id.** Each answer that a run writes, a model answer or a keyword-rule answer, has `run_id` (the UUID of the run) in its tags. The run row holds the hints and the `prompt_digest`, so the id of an answer leads to the hints that produced it. A superseded answer keeps its run id.
- **Feedback, acceptance & superseded drafts (#3056, #2926).** `accept` persists `accepted_by_user=True` on the draft's `tags` so subsequent re-ask runs preserve user confirmation. Feedback on a draft superseded by a newer suggestion (`status=SUPERSEDED` and `superseded_by_id IS NOT NULL`) returns `409 Conflict` with `superseded_by_id` and `live_suggestion_id` without writing `AiFeedback`. User-rejected drafts (`superseded_by_id IS NULL`) and `APPLIED` rows still record audit feedback. Low-confidence tier counts and replay proportions emit bounded OTEL telemetry (`finance.extraction.confidence_tier`, `finance.correction_loop.low_confidence_proportion`). A shutdown of the API process cancels its classify task: the run stays `running` until the reaper fails it with `heartbeat_lost` after 5 minutes. The candidate auto-approve after the last batch has no heartbeat and no deadline of its own. The `timeout=60` of a batch call is a limit for each read of the stream, not a total (UNVERIFIED). The 180 s deadline covers the plan, the rule answers and every batch.
- **Run again panel and 422.** The panel of the statement page offers "Extract again" and "Classify again" for a parsed statement. The default is classify for a CSV and extract otherwise. A 409 with `active_run_id` says that a run is in progress. A 422 body keeps only `loc`, `msg` and `type` of each error: the `input` and `ctx` fields are dropped, and a `msg` can hold validator text.

## Account Coverage Contract

- `GET /api/statements/coverage` checks adjacent approved statements per account/currency against `BALANCE_TOLERANCE` (`0.001`) and `CROSS_PERIOD_GAP_PLUG_TOLERANCE` (`0.10`), surfacing `GAP`, `OVERLAP`, or `DUPLICATE` issues while exempting zero-change gaps (`|delta| <= 0.10`) and daily broker snapshots.
